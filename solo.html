01 Problem

흩어진 도구, 연결되지 않는 데이터, 머릿속에만 있는 룰

프리랜서 5명을 인터뷰하고 본인 경험을 더해 페인포인트를 매핑했다. 페르소나는 두 명. 같은 사람의 시간 축 위 다른 단계로 보아도 무방하다.

PRIMARY
막 시작한 프리랜서, 31세
대기업 마케터 3년차 → 6개월 전 퇴사
프리랜서 마케팅 컨설턴트 · 월 2~3개 프로젝트
현재 사용 중인 도구
한글 (견적서) 노션 카톡 + 이메일 홈택스 엑셀 토스/은행앱
주요 페인
  • 이번 달 얼마 받지? — 5분간 계산기 두드림
  • 미수금 추적 안 됨, 입금 확인은 매일 수동
  • 새 견적 만들 때마다 양식부터 다시 짬
  • 부가세·원천징수 매번 헷갈림
SECONDARY
베테랑 프리랜서, 38세
프리랜서 개발자 7년차
월 5~8개 프로젝트 · 장기 리테이너 3곳 · 회계사 위임
현재 사용 중인 도구
노션 + 자체 템플릿 Zapier 자동화 회계사 (월 15만원)
주요 페인
  • 시스템은 있지만 셋업·유지에 매월 5시간
  • 클라이언트별 단가·할인율이 머릿속에만 있음
  • "이전에 비슷한 거 얼마 받았더라" 검색 어려움
  • 회계사 비용은 부담, 직접 하면 시간 부담

7가지 페인포인트를 3개로 압축했다

각 페인은 다른 페인을 만든다. 표면 증상이 아닌 상위 원인으로 정리했다.

PAIN 01 / 가시성
"내 수익이 안 보인다"
이번 달 얼마 들어올지, 미수금이 얼마인지, 작년 대비 어떤지 — 매번 엑셀 열어 계산해야 한다. 데이터는 다 있지만 연결이 안 된다.
PAIN 02 / 반복
"행정 작업이 매번 처음부터다"
견적서·계약서·인보이스를 만들 때마다 양식부터 다시 짜고, 부가세 계산하고, 클라이언트 정보 복붙한다. 템플릿화·자동화의 부재.
PAIN 03 / 암묵지
"내 비즈니스 룰이 머릿속에만 있다"
이 클라이언트는 단가 얼마, 저 클라이언트는 후불, 이런 일은 추가비 — 모두 머릿속에. 까먹어서 손해 본 적이 많다.
02 Hypothesis

3개의 페인 → 3개의 솔루션 가설

페인포인트를 그저 나열하는 게 아니라, 각각을 어떤 가설로 풀 것인지 명시했다. 가설은 곧 의사결정의 근거가 된다.

Pain 01
수익이 안 보인다 — 견적·계약·인보이스·입금이 따로 논다
→
Solution Hypothesis
단일 데이터 흐름 — 한 프로젝트의 상태 변화로 묶고 대시보드에서 자동 집계
Pain 02
행정이 매번 처음부터다 — 반복 작업의 템플릿화 부재
→
Solution Hypothesis
한 번 입력, 연쇄 생성 — 견적 정보가 인보이스·계약서로 자동 흐름 + 세금 정책 내장
Pain 03
룰이 머릿속에만 있다 — 개인의 암묵적 정책을 시스템화하지 못함
→
Solution Hypothesis
개인 정책의 데이터화 — 클라이언트·작업유형별 룰을 명시적으로 저장하고 견적 작성 시 자동 적용
03 Key Decisions

3개의 핵심 의사결정과 트레이드오프

제품의 형태를 결정한 세 갈래의 갈림길. 각각에서 무엇을 선택했고, 무엇을 포기했는지 명시한다. 좋은 PM 결정은 트레이드오프를 숨기지 않는다.

01 / IA

"프로젝트 중심" vs "클라이언트 중심" 정보 구조

Pain 01(수익 가시성)을 풀려면 데이터를 어떤 축으로 묶을 것인가. 1차 객체가 무엇이냐가 모든 화면의 형태를 결정한다.

✓선택 · 옵션 A

프로젝트 중심

1차 객체는 프로젝트. 클라이언트는 강력한 보조 축으로 별도 프로필 페이지에서 관계 이력을 누적.

+ 진행 상황 직관, 단발 작업에 자연스러움
− 같은 클라이언트의 여러 프로젝트가 흩어짐
옵션 B

클라이언트 중심

1차 객체는 클라이언트. 모든 프로젝트는 클라이언트 하위에 종속.

+ 장기 거래·관계 이력에 유리
− 단발 의뢰가 어색함 (1프로젝트 1클라이언트인데 굳이 2단계?)
✓근거

주 페르소나(초보 프리랜서)의 작업은 단발 프로젝트가 80%. "수익이 안 보임"의 핵심은 "지금 진행 중인 일"이므로 프로젝트가 1차 축이어야 대시보드가 직관적이다.

!포기한 것 / 완화

베테랑 페르소나의 "이 클라이언트와 작년에 뭐 했지?" 조회가 2단계가 됨. → 클라이언트 상세에 거래 타임라인과 인사이트를 두텁게 배치해 보완.

02 / TAX

세금 처리, 자동 vs 수동 vs 자동+오버라이드

Pain 02(반복 작업)의 핵심 — 부가세·원천징수를 어디까지 자동화할까. 자동화의 효율과 사용자 통제권의 균형.

옵션 A

완전 자동

시스템이 룰 기반 자동 계산. 사용자 수정 불가.

+ 빠름, 실수 적음
− 예외 케이스(해외, 면세) 처리 불가
옵션 B

완전 수동

매번 사용자가 직접 입력. 시스템은 양식만 제공.

+ 모든 케이스 대응 가능
− 페인포인트 미해결, 매번 입력 부담
✓선택 · 옵션 C

자동 + 오버라이드

자동 계산 + 사용자가 필요시 변경 + 근거 항상 노출.

+ 90% 자동화 + 10% 예외 보장
− UI/데이터 모델 복잡도 ↑
✓근거

한국 프리랜서 세무 룰은 명시적이라 자동화 가능 영역이 90% 이상. 다만 자동 계산은 사용자가 의심하면 망하므로, 계산 근거를 항상 노출해 신뢰를 확보한다.

!포기한 것 / 완화

데이터 모델이 복잡해짐 (사용자 사업자 유형 + 클라이언트 유형 매트릭스). → 첫 사용 온보딩에서 1회 입력으로 끝나도록 설계.

03 / DOC

견적서 양식, 자유 vs 표준화 vs 구조화+커스텀

Pain 03(암묵지)을 풀려면 견적서를 어떻게 구조화할까. 자유도와 데이터 활용성의 균형.

옵션 A

자유 양식

한글·워드처럼 빈 캔버스에 모든 게 자유.

+ 무한 유연성
− 텍스트 덩어리, 데이터 활용 불가
옵션 B

완전 표준화

정해진 필드만 입력 가능 (제목·항목·금액·기간).

+ 데이터 재활용, 인보이스 자동 변환
− 협상 과정의 "맥락" 표현 불가
✓선택 · 옵션 C

구조화 + 커스텀

표준 필드 6개 + 자유 메모 영역.

+ 80%의 데이터화 효과 + 20% 자유도
− 사용자가 "어디까지 표준?" 학습 필요
✓근거

옵션 A는 페인포인트 미해결, 옵션 B는 현실 케이스 일부 누락. 옵션 C는 "표준 필드 6개로 90% 케이스 커버"의 균형점이며, 표준 필드를 기반으로 인보이스·계약서 자동 변환이 가능해진다.

!포기한 것 / 완화

특수 견적(성과 기반 보수 등)은 표현 어려움. → 자유 메모 영역에서 보완하되, 자유 영역은 인보이스 자동화 대상이 아님을 명시.

04 Policy Design

보이지 않는 룰의 설계

UI는 빙산의 일각이다. 자동 계산 한 줄 뒤에는 결정 트리가, 자동 변환 한 클릭 뒤에는 데이터 흐름의 정의가 있다. 이 챕터는 화면 너머의 정책을 정리한다.

4.1 세금 처리 결정 트리

사용자(나)의 사업자 유형과 클라이언트 유형의 조합으로 부가세·원천징수가 자동 결정된다. 견적·인보이스 작성 시점에 시스템이 다음 순서로 판단한다.

STEP 01

사용자 사업자 유형

미등록 · 부가세 X · 원천징수 3.3% 차감
간이과세자 · 부가세 면제 (1.5~4% 차등)
일반과세자 · 부가세 10% 추가
STEP 02

클라이언트 유형

사업자 · 세금계산서 발급
개인 · 현금영수증
해외 · 영세율 적용
STEP 03

결과 표시

자동 계산 + (?) 아이콘 → 클릭 시 근거 노출
사용자 오버라이드 가능 + "수정됨" 뱃지

5가지 케이스 결과 매트릭스 — 청구액 ₩1,000,000 기준

사용자 유형 클라이언트 유형 견적 표시 금액 실수령 비고
미등록 프리랜서 사업자 1,000,000 967,000 3.3% 원천징수
미등록 프리랜서 개인 1,000,000 1,000,000 원천징수 없음
간이과세자 사업자 1,000,000 1,000,000 간이세 별도 신고
일반과세자 사업자 1,100,000 1,100,000 VAT 10% 가산
일반과세자 개인 1,100,000 1,100,000 현금영수증 발급

4.3 클라이언트 정책 매트릭스

Pain 03("머릿속 룰")의 직접 해결. 클라이언트 프로필에 결제 조건·기본 단가·세금 처리·선호 결제수단을 저장하고, 새 견적 작성 시 자동 적용한다. 머릿속 룰을 명시적 데이터로 옮기는 것이 핵심.

결제 조건 완료 후 30일
기본 단가 ₩300,000/일
세금 처리 사업자 · VAT 10%
선호 결제수단 계좌이체
평균 입금 지연 11.7일 (자동 산출)
정책 충돌 시 우선순위

동일 항목에 여러 정책이 있을 때 적용 순서

  1. 1 견적 작성 시 직접 입력
  2. 2 해당 클라이언트 정책
  3. 3 작업 유형별 기본값
  4. 4 시스템 기본값

4.4 자동화의 함정과 4가지 방어 장치

자동화는 사용자가 의심하는 순간 망한다. 이 제품의 핵심은 자동화 자체가 아니라, 자동화에 대한 신뢰를 어떻게 만들 것인가이다.

1
계산 근거 항상 노출

부가세 옆 (?)아이콘 → "당신: 일반과세자, 클라이언트: 사업자 → VAT 10%"

2
변경 이력 표시

자동값 수정 시 "기본값 ₩100,000 → 수정됨" 뱃지로 의도성 확인

3
임계점 사전 알림

간이→일반 전환 임계점(연 매출 8천만원) 근처 시 미리 경고

4
한계 명시

복잡 케이스(해외 송금 등)에는 "세무사 상담 권장" 뱃지로 한계 인정

앞 장의 의사결정이 그대로 화면 구조가 된다. 1차 네비게이션은 프로젝트가 첫 항목, 클라이언트는 그 다음. 견적은 단독 메뉴가 아닌 프로젝트의 하위 객체.

06 Design System

의사결정의 일관된 시각 언어

디자인 시스템은 컴포넌트 모음이 아니다. 앞 장의 모든 결정을 시각 토큰으로 번역한 결과다. 색·타이포·간격·인터랙션 모두에 의도가 있다.

컬러 — Trustworthy Calm

Stripe·Mercury 톤. 정산·세금 도구는 신뢰감이 가장 중요. 화려함 < 정제됨.

Neutral
Primary
Info
Warning
Danger

→ Neutral은 차가운 회색이 아닌 따뜻한 베이지. Primary는 파랑이 아닌 Teal/Green — "초록=수익"의 한국 사용자 연상 활용. Info는 자동 영역, Warning은 미수금, Danger는 연체에 한정.

타이포 — Pretendard + Mono

한글 본문은 Pretendard, 숫자는 모노스페이스로 자릿수 정렬.

h1 / 24·500 대시보드
h2 / 18·500 진행 중 프로젝트
body / 14·400 A사와의 로고 리뉴얼 작업
mono / 14·500 ₩3,520,000
caption / 12 2026.04.22 ~ 05.15

→ 굵기는 400과 500 단 두 개만. 700은 사용 안 함 (Stripe·Linear 톤). 숫자는 항상 mono로 정렬 가능성 확보.

컴포넌트 — 의미를 가진 변형

같은 컴포넌트가 의미에 따라 자연스럽게 변형된다. 4가지만 있으면 충분.

견적 작성 — 정책 설계의 시연 무대

본 포트폴리오의 하이라이트. 의사결정 2(자동+오버라이드)와 의사결정 3(구조화 견적서)이 모두 시각화된다.

프로젝트 상세 — 1차 축의 핵심

의사결정 1의 결과물. 5단계 진행바와 가변 마일스톤의 이중 구조로 객체 라이프사이클을 두 추상화 단계로 보여준다.

  • 진행 바 = 5개 고정 (라이프사이클) / 마일스톤 = 가변 (사용자 일정)
  • 마일스톤 행: 완료(회색) / 진행(파랑 강조) / 예정(투명도↓)
  • 금액 카드 4단 — "잔여 ₩2,560,000"이 가장 큰 글씨 + 노란 강조

08 Reflection

회고 — 무엇을 배웠고, 무엇을 못 했는가

4주의 단독 기획. 가설은 충분히 검증되었지만, 한계도 명확하다. 다음 버전으로 이어가야 할 것을 정리한다.

✓ Gained

얻은 것

  • "정책 설계 → IA → UI" 의 인과 관계를 한 사이클 직접 경험
  • 자동화 UX는 기능이 아닌 "신뢰 확보의 룰"이라는 통찰
  • 같은 컴포넌트가 의미에 따라 변형되는 의미 기반 디자인 시스템
  • 페르소나 2명 구조가 단순함과 확장성을 동시에 보여준다는 발견
! Limitations

못한 것 / 한계

  • 실제 사용자 인터뷰 5명은 본인 네트워크 한정 — 샘플 편향 가능
  • 모바일 화면 미설계. 정산 도구 특성상 데스크톱 우선이지만 모바일도 필요
  • 온보딩 플로우 미설계 — 첫 사용 시 사업자 정보 입력 UX가 가설로만 존재
  • 실제 사용자 테스트 미진행 — A/B 테스트로 검증해야 할 가설 6개 남음

다음 단계 (Roadmap)

  1. v0.1 — 핵심 흐름 구현. 견적 작성 → 인보이스 발급 → 입금 확인의 기본 데이터 흐름. Next.js + Tailwind + Supabase
  2. v0.2 — 모바일 반응형. 입금 확인·미수금 추적 같은 "외출 중 빠르게" 시나리오를 모바일 우선 설계
  3. v0.3 — 베타 사용자 5명 확보. 실제 프리랜서 5명의 1개월 사용 데이터로 6개 가설 검증
  4. v1.0 — 정식 출시. 클라이언트 정책 자동화, 세금 신고 보조, 회계사 데이터 export까지 완성
